# Delivery OS — Architecture & Contracts

**Status:** Normative technical specification
**Parents:** [Product Plan](product-plan.md), [Domain Model & Workflows](domain-workflows.md)
**Related:** [Design System](design-system.md), [AI, Security & Evaluation](../assurance/ai-security-evaluation.md), [Delivery Backlog](../planning/delivery-backlog.md)

## 1. Architecture Decisions

### 1.1 Style

Delivery OS is a TypeScript modular monolith with separate web and worker runtimes sharing one domain/application codebase and PostgreSQL database.

It is not a distributed microservice system during the pilot. Modules may interact only through exported application interfaces and domain events; direct cross-module table access is prohibited outside read-model code explicitly documented for reporting.

### 1.2 Repository layout

```text
apps/
  web/                 Next.js UI, internal HTTP API, Better Auth, MCP endpoint
  worker/              BullMQ consumers and scheduled jobs
packages/
  domain/              Entities, value objects, policies, state machines
  application/         Commands, queries, transactions, authorization
  database/            Drizzle schema, migrations, repositories, outbox
  contracts/           Zod schemas, error codes, internal API and MCP DTOs
  auth/                Better Auth configuration and permission adapters
  ingestion/           Storage, scanning, parsers, OCR adapters
  ui/                  Source-owned design system, shadcn components, tokens
  ai/                  Provider adapters, prompt registry, validation, eval hooks
  observability/       Logging, metrics, tracing, audit helpers
  test-support/        Factories, fixtures, fake providers, client simulators
services/
  ocr/                 Stateless, self-hosted PaddleOCR Python runtime
docs/                  Indexed product, engineering, research, and operations specifications
```

Use pnpm workspaces. Local development uses Docker Compose. All database changes use checked-in Drizzle migrations; application startup never auto-generates or silently applies schema changes in production.

### 1.3 Runtime and infrastructure

| Capability | Pilot choice |
|---|---|
| Web/API/MCP | Next.js on Railway |
| Worker | Node.js service on Railway |
| OCR runtime | Private Python service on Railway; CPU-first, horizontally bounded |
| Database | Railway PostgreSQL |
| Queue/rate-limit cache | Railway Redis + BullMQ |
| Source/export storage | Cloudflare R2 through S3-compatible adapter |
| Local object storage | MinIO in Docker Compose |
| OCR | Self-hosted PaddleOCR, PP-StructureV3 coordinate-preserving pipeline |
| Authentication/OAuth | Better Auth |
| Email | Resend through provider adapter; signed delivery webhooks |
| Error/performance monitoring | Sentry with OpenTelemetry instrumentation |
| Logs | Structured JSON to Railway plus external retention if required |

Railway services do not rely on Compose `depends_on`; web and worker use bounded exponential startup retries and health/readiness probes.

Production uses a private Cloudflare R2 bucket in the approved jurisdiction when residency is required. Bucket-scoped R2 API tokens separate runtime read/write access from operational lifecycle and backup access. OCR runs only in Delivery OS-controlled infrastructure; no source page or OCR text is sent to an external OCR API. “Free OCR” means no per-page, model-license, API, or subscription fee; ordinary compute, storage, and operations costs remain.

## 2. Module Boundaries

1. **Identity & Access** — Better Auth integration, workspaces, membership, permissions.
2. **Projects & Clients** — client records, projects, lifecycle, calendars, team availability.
3. **Artifacts** — Drafts, Review Snapshots, Baselines, Deltas, approvals, comments, audiences.
4. **Ingestion** — source storage, scanning, parsing, OCR, claims, citations, conflicts, gaps.
5. **Planning** — Technical/UX plans, Modules, Features, Feature Specs, traceability, forecasts.
6. **Delivery** — typed work, DoR/DoD, sprints, blockers, reports, review, completion snapshots.
7. **Changes** — Client Input, materiality, Impact Reports, Change Sets, successors.
8. **Costs** — optional items, currencies, manual rates, snapshots, views.
9. **Agent Gateway** — OAuth resource server, MCP resources/tools, workflow pack.
10. **Platform** — audit, outbox, jobs, notifications, exports, search, retention, observability.

Every mutation enters through an application command. Commands load effective permissions, validate expected revision and state, transact domain changes plus outbox/audit records, then return a versioned DTO.

## 3. Data and Persistence

### 3.1 PostgreSQL conventions

- UUIDv7 IDs generated by the application.
- `workspace_id` on every tenant record and in every relevant composite index.
- `project_id` on every project-owned record.
- UTC timestamps; project/workspace time zones are IANA names used only for display/scheduling.
- Fixed-precision `numeric` for money, rates, and calculated totals; never floating point.
- `jsonb` only for versioned snapshot bodies, validated generated output, and provider metadata—not as a substitute for core relational fields.
- Soft-delete/tombstone columns only for recoverable deletion; ordinary lifecycle uses explicit states.
- Foreign keys and uniqueness constraints enforce invariants where possible.

### 3.2 Concurrency and idempotency

- Mutable aggregates contain integer `revision`.
- Internal and MCP mutations require `expectedRevision`.
- Mismatch returns HTTP `409` / MCP domain error `REVISION_CONFLICT`.
- Mutating commands accept `idempotencyKey`; completed command results are retained for the retry window.
- Approval decisions, Change Set application groups, queue jobs, exports, notifications, and purge are idempotent.

### 3.3 Transactional outbox

The same database transaction stores:

- Aggregate mutation.
- Audit Event.
- Outbox Event.
- Idempotency result placeholder/completion.

The worker publishes/processes outbox events at least once. Consumers deduplicate by event ID. No email, queue publish, object delete, or AI call happens inside the database transaction.

### 3.4 Artifact snapshots

- Canonical snapshot JSON is schema-versioned and deterministically serialized.
- Store SHA-256 content hash and immutable metadata in PostgreSQL.
- Large rendered exports remain in object storage and reference the snapshot hash.
- Snapshot schemas are backward-readable; migrations transform read models, never rewrite historical bodies without an explicit migration record.

### 3.5 Work estimates and calibration

Store AI-aware estimates as versioned structured records, not loose labels:

```ts
type WorkEstimate = {
  vdeHours: { low: number; high: number };
  size: "XS" | "S" | "M" | "L" | "XL";
  elapsedHours: { low: number; high: number };
  machineBudget?: { runtimeMinutes?: number; cost?: string };
  aiFit: "A0" | "A1" | "A2" | "A3";
  uncertainty: "U0" | "U1" | "U2" | "U3";
  consequenceRisk: "R1" | "R2" | "R3" | "R4";
  basis: "COLD_START" | "COMPARABLE_HISTORY" | "EXPERT_DECOMPOSITION";
  drivers: string[];
  assumptions: string[];
  toolProfile?: {
    tool: string;
    model?: string;
    workflowVersion?: string;
    repositoryArea?: string;
  };
};
```

The server derives/validates size from the VDE high bound and enforces U3/XL/R3/R4 readiness rules. At start, freeze the estimate revision. At Done, store aggregate actual VDE band and elapsed cycle time without creating per-person timesheets. Calibration queries are tenant-scoped and group comparable work/tool/risk profiles; agent activity counts are never productivity scores.

## 4. Authentication and Authorization

### 4.1 Better Auth

Enable:

- Email/password with verified email.
- Magic Link.
- Two-Factor Authentication using TOTP and recovery codes.
- Admin/session management.
- OAuth 2.1 Provider and JWT/JWKS support needed by the MCP resource server.

Better Auth authenticates the principal. Delivery OS application policies authorize workspace/project actions.

### 4.2 Privileged step-up

Admin operations, workspace deletion/export, role elevation, emergency project override, and MCP client authorization require a `mfa_verified_at` no older than 10 minutes.

Magic-link sessions do not count as MFA. The UI redirects to a TOTP challenge before the privileged command.

### 4.3 Sessions

- Session cookies are `HttpOnly`, `Secure`, and `SameSite=Lax` or stricter where flows permit.
- Rotate sessions after sign-in, password change, MFA enrollment, and privilege change.
- Users can list and revoke sessions.
- Deactivation revokes all sessions and OAuth grants.

### 4.4 Authorization evaluation

Every repository/query requires an `AuthorizationContext`:

```ts
type AuthorizationContext = {
  userId: string;
  workspaceId: string;
  projectId?: string;
  workspaceRole: "ADMIN" | "MEMBER";
  projectRoles: ProjectRole[];
  oauthClientId?: string;
  oauthScopes?: string[];
  mfaVerifiedAt?: string;
};
```

Authorization is deny-by-default. UI hiding is never a security control.

## 5. Frontend and Design System

### 5.1 Stack and ownership

- Use the current stable Next.js/React line, Tailwind CSS v4, and `shadcn@latest`, with exact versions committed to the lockfile.
- Initialize shadcn explicitly with Base UI (`--base base`). Base UI is the only third-party primitive layer.
- `@radix-ui/*` and `radix-ui` packages are prohibited direct or transitive application dependencies; CI checks the lockfile and dependency graph.
- shadcn is a source-code accelerator, not a runtime design-system dependency or finished visual identity. Generated files are reviewed, owned, tested, and evolved in `packages/ui`.
- Application code consumes `@delivery-os/ui` exports and never imports Base UI directly. Exceptions require an ADR and a corresponding design-system wrapper in the same change.

### 5.2 Component layers

1. **Tokens** — semantic color, typography, spacing, radius, elevation, motion, focus, density, and data-visualization tokens.
2. **Primitives** — reviewed shadcn-generated components backed by Base UI.
3. **System components** — Delivery OS components such as `StatusBadge`, `RiskIndicator`, `EvidenceList`, and `ApprovalBanner`.
4. **Domain patterns** — composed, tested flows such as approval panels, traceability tables, work cards, gap/conflict review, and client visibility preview.

Tailwind v4 uses CSS-first configuration: `@import "tailwindcss"`, `@import "tw-animate-css"`, semantic CSS variables expressed in OKLCH, and `@theme inline`. The shadcn `components.json` uses CSS variables, a blank Tailwind config path, monorepo aliases into `packages/ui`, and the Base UI registry. Prefer package imports/exports for monorepo boundaries.

Server Components are the default. Add `"use client"` only at the smallest interactive boundary. Style Base UI state through its documented data attributes and the shadcn `data-slot` hooks; do not couple application code to undocumented generated markup.

### 5.3 Quality gates

- Each primitive/system component has states for default, hover, focus-visible, disabled, loading, empty, error, and destructive behavior when applicable.
- Keyboard, focus management, accessible names, contrast, reduced motion, zoom/reflow, touch target, and screen-reader behavior are verified to WCAG 2.2 AA.
- Storybook or an equivalent isolated component harness provides visual/a11y fixtures; critical patterns also receive Playwright coverage.
- Component changes include a visual-regression review and a short upgrade note when regenerated from shadcn.
- Full design principles and governance are normative in [Design System](design-system.md).

## 6. Object Storage and Ingestion

### 6.1 R2 and MinIO configuration

- Production bucket is Cloudflare R2 with public `r2.dev` and custom-domain access disabled; local development uses private MinIO.
- Cloudflare-managed AES-256 encryption at rest and TLS in transit are mandatory. R2 does not support AWS SSE-KMS headers; the adapter must not claim or require SSE-KMS parity.
- R2 S3 bucket versioning is unavailable. Every logical revision uses a new immutable object key; the application never overwrites a committed source/export object.
- PostgreSQL stores an `ObjectManifest` row for every immutable key, SHA-256, logical generation, state, and retention deadline. Recovery and purge operate from this manifest rather than provider versions.
- Separate prefixes for `quarantine/`, `sources/`, `exports/`, and `purge-receipts/`.
- R2 lifecycle rules abort incomplete multipart uploads and may expire explicitly disposable exports; source recovery/purge is application-controlled.
- Runtime credentials are bucket-scoped Object Read & Write. Lifecycle, backup, and destructive administration use separate operational credentials not available to web or worker.
- Application uses short-lived S3 Signature V4 presigned PUT/GET URLs bound to a generated object key and expected metadata. The service validates MIME, size, and a full-object SHA-256 after upload before processing because presigned URLs are bearer capabilities and S3-compatible checksum behavior varies.
- Downloads re-authorize the user before issuing a signed URL.
- If residency is required, create the R2 bucket with a jurisdictional restriction; location hints alone are not a residency guarantee.
- A separate backup bucket/account path with independent credentials receives daily immutable-key copies and manifests. Restore drills verify database references, primary objects, and backup recovery.

### 6.2 Upload flow

1. Internal API creates `SourceArtifact` in `QUEUED` and returns constrained presigned upload.
2. Client uploads with checksum.
3. Completion command verifies object metadata and enqueues scan.
4. Worker streams object through malware scanner in quarantine.
5. Failed scan moves record to `FAILED`; object is inaccessible and scheduled for deletion.
6. Valid object is copied/promoted to `sources/`, then parsed.
7. Parser creates normalized blocks and source locators.
8. OCR is invoked only when deterministic parsing classifies one or more PDF pages as image-only or unusable. The worker renders only required pages to bounded images and submits them to the private PaddleOCR service.
9. Extraction/claim generation begins only after deterministic processing succeeds.

Supported pilot files are PDF/OCR, DOCX, Markdown, and text; 50 MB/file and 500 MB/project.

### 6.3 Parser and OCR adapters

```ts
interface DocumentParser {
  supports(input: DetectedDocument): boolean;
  parse(input: StoredObjectRef): Promise<NormalizedDocument>;
}

interface OcrEngine {
  recognize(input: OcrPageBatch, request: OcrRequest): Promise<NormalizedOcrDocument>;
}
```

Use deterministic local TypeScript parsing where it passes citation fixtures. The pilot OCR adapter calls a stateless, private Python service running a pinned PaddleOCR PP-StructureV3 pipeline because it emits fine-grained text/table coordinates needed for exact citations. The service receives rendered page images from the worker, has no production object-store credentials, and returns schema-validated blocks containing page, polygon/bounding box, text, confidence, reading order, and structure metadata.

OCR model artifacts are baked into the versioned service image and verified by digest; production startup never downloads or executes remote model code. Network egress is denied after image build. Requests and results are deduplicated by source/page hash plus renderer and OCR configuration versions. Timeouts, malformed output, low-confidence pages, and service exhaustion leave the source in `Needs Attention`; they never silently produce accepted text.

PaddleOCR is selected over Unlimited OCR for the pilot because it has a mature Apache-2.0 project, established deployment paths, CPU support, and coordinate-preserving structured output. Unlimited OCR remains an evaluation candidate and cannot be promoted without the gates in [OCR Evaluation](../research/ocr-evaluation.md).

## 7. Background Jobs

Queues:

- `ingestion.scan`
- `ingestion.parse`
- `ingestion.ocr`
- `ai.extract`
- `ai.specify`
- `ai.breakdown`
- `ai.impact`
- `exports.render`
- `notifications.send`
- `retention.purge`
- `outbox.dispatch`

Every job stores workspace/project, job type, schema version, input reference/hash, status, progress, attempts, next retry, error code/safe message, and correlation ID.

Retry only transient errors. Validation, malware, unsupported format, and permission errors go directly to `Needs Attention`/dead-letter. Users may cancel jobs that have no committed domain result.

BullMQ is the only application job system. OCR work uses the same durable job, retry, cancellation, and dead-letter contracts as other background work. Queue concurrency is bounded independently from the OCR service’s CPU/memory capacity.

## 8. AI Provider Contract

```ts
interface AiWorkflow<I, O> {
  readonly workflowId: string;
  readonly inputSchemaVersion: string;
  readonly outputSchemaVersion: string;
  run(input: I, context: ApprovedContext): Promise<ValidatedGeneration<O>>;
}

type ValidatedGeneration<T> = {
  data: T;
  provenance: GenerationProvenance;
  validation: ValidationFinding[];
  citations: CitationRef[];
  usage: { inputTokens?: number; outputTokens?: number; cost?: string };
};
```

- Providers are selected by evaluated workflow configuration, not by workspace users.
- Prompts are versioned code/config artifacts.
- Outputs use strict schema validation; invalid output is never persisted as an accepted proposal.
- Provider calls are asynchronous, timeout-bounded, retry-classified, and budgeted.
- Full rules and gates are in [AI, Security & Evaluation](../assurance/ai-security-evaluation.md).

## 9. Internal HTTP API

The browser uses same-origin, versioned JSON endpoints with Zod request/response schemas. There is no public REST commitment in the pilot.

Mutation envelope:

```json
{
  "expectedRevision": 12,
  "idempotencyKey": "019...",
  "command": {}
}
```

Success returns entity ID, new revision, state, relevant snapshot/action IDs, and correlation ID.

Stable error codes include:

- `UNAUTHENTICATED`
- `MFA_REQUIRED`
- `FORBIDDEN`
- `NOT_FOUND`
- `REVISION_CONFLICT`
- `INVALID_TRANSITION`
- `READINESS_FAILED`
- `APPROVAL_CLOSED`
- `MATERIAL_CHANGE_REQUIRED`
- `DEPENDENCY_CYCLE`
- `QUOTA_EXCEEDED`
- `JOB_NOT_CANCELLABLE`
- `VALIDATION_FAILED`

Never reveal cross-tenant existence through different `NOT_FOUND`/`FORBIDDEN` behavior.

## 10. MCP Contract

### 10.1 Transport and authorization

- Streamable HTTP MCP endpoint at `/mcp`.
- Better Auth OAuth 2.1 Provider supplies authorization server metadata, PKCE flow, consent, revocation, and JWKS.
- MCP endpoint publishes RFC 9728 Protected Resource Metadata.
- Validate issuer, signature, expiry, audience/resource, client, user, scopes, active session/grant, workspace/project access.
- Interactive user-delegated authorization only during pilot.

### 10.2 Scopes

| Scope | Allows |
|---|---|
| `project:read` | Read permitted approved context and project delivery state |
| `work:read` | Read permitted work, checklists, evidence |
| `work:start` | Ready → In Progress for authorized work |
| `work:update` | Allowed active status/blocker updates |
| `evidence:submit` | Submit implementation report and request In Review |
| `comment:write` | Add permitted comments |
| `change:propose` | Create proposed change; never approve/apply |

Scopes do not replace application authorization. Start with read scopes and request incremental elevation for writes.

### 10.3 Resources

- `deliveryos://projects/{projectId}/context`
- `deliveryos://projects/{projectId}/requirements/current`
- `deliveryos://projects/{projectId}/technical/current`
- `deliveryos://projects/{projectId}/ux/current`
- `deliveryos://features/{featureId}/specification`
- `deliveryos://work/{workItemId}`
- `deliveryos://sprints/{sprintId}`
- `deliveryos://templates/work/{type}`

Resources return compact approved context, snapshot IDs/hashes, trace links, audience-filtered content, and current revisions. Historical baselines require an explicit ID.

### 10.4 Tools

| Tool | Mutation |
|---|---|
| `list_projects` | No |
| `search_work` | No |
| `get_work_context` | No |
| `start_work` | Ready → In Progress |
| `record_blocker` / `resolve_blocker` | Blocker overlay |
| `submit_implementation_report` | Stores report and requests In Review |
| `add_comment` | Append-only comment |
| `propose_change` | Creates Proposed Change Request |

All mutating tools require `expected_revision` and `idempotency_key`. Tools cannot approve, apply Change Sets, or move work to Done.

### 10.5 Workflow pack

Ship a versioned, tool-agnostic workflow:

1. Authenticate and select workspace/project.
2. Select assigned Ready work.
3. Load approved Requirement, Technical, UX, Feature Spec, traceability, DoR/DoD.
4. Confirm no Blocking gap and start work.
5. Implement and validate in the user's external environment.
6. If intent must change, submit `propose_change`; do not silently diverge.
7. Submit structured implementation report.
8. Move to In Review and stop; a human decides Done.

Provide setup/test guides for Codex, OpenCode, and representative VS Code MCP clients.

## 11. Search, Notifications, and Exports

- PostgreSQL full-text indexes only Client/Team-visible fields with authorization filters applied before result return.
- Email is event-driven from outbox; invitations and pending actions are transactional.
- The Resend adapter sets an application notification ID for provider idempotency/correlation and records the provider message ID.
- `/webhooks/resend` verifies the raw-body webhook signature before parsing, rejects stale/invalid events, and deduplicates provider event IDs.
- Delivery, delay, bounce, complaint, and failure events update notification status and safe operational metrics. They never mutate project-domain state.
- In-app inbox items are deduplicated by recipient/event/entity.
- Exports are asynchronous snapshot-based jobs and re-evaluate audience/permission at request time.
- Pilot export formats: PDF for presentation, Markdown for portable human-readable content, JSON for machine portability.

## 12. Observability and Operations

- Correlation ID spans HTTP/MCP request, command, audit event, outbox, job, provider call, and notification.
- Metrics: request latency/errors, queue depth/age/retries/dead letters, database pool, object failures, auth/MFA/OAuth failures, AI latency/cost/validation/eval score, email delivery, purge lag.
- Sentry receives scrubbed application errors and traces from OpenTelemetry instrumentation. Source document text, client comments, credentials, signed URLs, authorization headers, cookies, and AI request/response bodies are excluded before export.
- Railway retains structured runtime logs; Sentry is not the audit store. Alert rules cover sustained error rate, queue age/dead letters, OCR saturation/latency/low-confidence failures, R2 errors, email bounce/complaint spikes, authentication abuse, and purge/backup failures.
- Health endpoint checks process; readiness checks database and required configuration, not external AI availability.
- AI/provider outage degrades only assisted operations; manual workflows remain healthy.
- Daily backups and documented restore process must satisfy RPO/RTO. Restore tests use a separate environment and validate PostgreSQL manifests plus primary and backup R2 objects.

## 13. Architecture Acceptance

- Module boundary lint/dependency tests pass.
- Migrations apply from empty database and prior pilot snapshot; rollback/forward-fix procedure is documented.
- Cross-tenant query and export tests pass.
- Duplicate commands/jobs produce one domain outcome.
- Stale mutations cannot overwrite current state.
- Web and worker restart without losing accepted commands.
- R2/MinIO contract tests pass without relying on unsupported R2 versioning or SSE-KMS behavior.
- OCR fixtures pass citation-coordinate, accuracy, resource, timeout, and malformed-output gates on the pinned self-hosted image.
- Dependency checks prove application code has no Radix UI package and uses only the approved UI package boundary.
- MCP conformance/auth tests pass on all target clients.
- Restore drill, load profile, WCAG, and security gates in [Pilot Scope](../planning/pilot-scope.md) pass.
